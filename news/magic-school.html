Magic School: from Unity to ScopeBee

Magic School was a Unity game. Now it runs on ScopeBee — the same game with the same code and art, and both builds are on this site, so the difference can be measured rather than described.

Play it in the browser

One game, two builds

This is not a small demo made for a benchmark: Magic School is a full game with locations, UI, animation and saves. Both builds print the same timing lines from the game code itself — when the preloader shows its first frame and when the main location does — so the load time is measured by the game, not guessed from the outside.

Results

What the move gave the game

  • A build 2.8 times smaller: 20.9 MB instead of 58.0 MB, and the player downloads 2.8 times less.
  • A start 5.9 times sooner: the main location is on screen in under a second rather than in almost six.
  • Almost no wait between the preloader and the game: 0.3 s on ScopeBee, 3.8 s on Unity.
  • 4.6 times less memory: 94.7 MB instead of 434.4 MB — the figure a phone browser runs out of first.

How it was measured

Each build was served from its own local server that serves only its folder in brotli, with caching off, so the speed of the connection stays out of the result. Every load is a cold one in a fresh Chrome profile on Apple Silicon, driven over the DevTools protocol; each figure is the median of five loads.

  • Build size — every file of the build folder on disk, as it is published.
  • Transferred — what the server actually sent, by its own log.
  • Resources — the same files after decompression.
  • Preloader and main location on screen — the lines the game prints on its first frame of each, performance.now() counted from opening the page, download included.
  • Heap Snapshot — a heap snapshot of the page ten seconds after the main location appears, after garbage collection.

The Unity build is Unity 6000.4. For how the other engines compare on a smaller game, see the engine comparison.
